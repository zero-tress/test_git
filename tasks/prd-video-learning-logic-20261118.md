本轮目标是把现有单视频特例学习与跨样本知识归纳的逻辑补齐，完成任务图①—⑦的视频学习部分。复用已有流程和输出，不重建项目。

用户在本次对话中已确认：保留现有图的样式、布局方式和交互，但允许修正分析数据中的节点、关系、条件及门控含义。因此：

- 沿用已有约定：图的结束节点前不新增完成门控；任务完成评价仍在知识数据与现有详情中保留。
- 所有视频内容理解、技能分类、成败判断、条件归纳和语义合并由服务器8032的 Qwen3.8-27B完成。Codex不观看视频替模型下结论。

- 本轮不建设机器人控制器、行为树运行时、LLM规划或执行反馈闭环，不改数据库及服务，也不重做相机补偿、活动分数等前处理模块。

## 2. 要实现的两级结果

### 单视频：形成可复核的特例知识

单个视频处理到“独立观察 → 意图一致性校验 → 技能实例及局部结果 → 候选条件/规则 → 单案例校验与固化”即完成。

应保存：
1. 总任务候选与共存子任务、期望效果、支持/反对证据、同步前后置信度。
2. 实际动作、实体、状态变化、时间与观察关系；冻结同步前的观察分支。
3. G_case中的语义技能实例及其完整操作实现，每次尝试单独标识。
4. success / failure / not_executed / unknown 四种局部结果，与整体任务结果分开。
5. 候选前置、过程约束、预期后置、实际后置及评价依据，区分观察、模型推断和显式政策。
6. 核心动作切片、准备上下文、结果验证上下文、时间偏移、原视频与切片哈希。
7. 引用、时序、任务范围及证据一致性报告。

不要求一个普通单视频独立学出普遍必要条件。清晰视频不强制生成多个互斥意图；可以共存的子任务不当作互斥候选归一化。

拿笔政策可以保持语义层线性链，通用任务仍保留实际偏序。实现层的并行、保持、交替等不能因上层视图线性而删除，也不能为了凑类型把它们强行提升为语义技能间关系。

### 多视频：开展两条互相关联的学习线

**学习线A：同目标的完整任务图。**
比较各视频的目标与效果，进行共同节点对齐、成功支路合并、功能合并，得到语义技能及多个完整实现R。任务目标不同的案例不直接混成同一个任务主图。

**学习线B：同类技能实例与切片。**
按局部目的、效果及可比情境组织样本，比较成功、失败、未执行与未知实例，学习适用条件、约束、完成依据与失败因素。样本可以来自不同任务视频，也可以来自同视频的不同尝试。

完整源案例全部保留。成功流程进入成功主图；失败尝试进入条件对照，不能被删除或冒充成功实现。整体任务失败中的局部成功可以参与技能学习，但不冒充完整任务成功示范。

## 4. 分步改动与验收条件

### US-001：把通用规则与任务专用政策分开（P0）

作为使用者，我希望新视频遵循自己的任务要求，拿笔案例的特殊规定只在显式选择时生效。

拟改：
- video2op/case_graph.py 的SYSTEM、自检清单及learn。
- video2op/semantic_aggregation.py 的GRAPH_SYSTEM、自检清单及learn。
- run.py、tools/learn_video_knowledge.py、tools/learn_semantic_graph.py 的政策传递。
- tasks/pick_pen_graph_requirements_v2.json仅作为拿笔实例政策，必要时增加带版本的新政策，保留原文件作历史依据。

具体做法：
- 通用提示只规定证据、字段、未知处理和不虚构。
- 线性链、必须从靠近进入、特定分支、排除目标达成后的释放/放置，均由显式政策注入，提示和验证共用同一政策。
- 任务目标、目标对象、成功判据及完成范围在运行开始时冻结。拿笔按“持有并离开原支撑”评价；要求最终持续持有或包含放置的其他任务按自己的判据评价。
- 目标先达到后又发生后续动作，与“最终状态必须满足”两种口径不能混用；用明确任务契约记录，不由宿主事后改目标。

验收：
- [ ] 未提供政策时，模型请求中没有拿笔专用骨架、禁放置规则或强制靠近规则。
- [ ] 通用搬运/放置测试保留必要的release/place。
- [ ] 显式拿笔政策下，超出任务范围的动作仍保存在观察证据中，并说明为何不进入任务技能图。
- [ ] 续跑时目标/政策变化触发明确的版本检查，不静默复用旧结论。

### US-002：保留单视频事实、尝试与完整实现（P0）

作为使用者，我希望看到本视频发生的事，并能区分技能目的、一次尝试和它的操作实现。

拟改：
- video2op/case_graph.py、video2op/pipeline.py。
- 仅在接口需要时小改skill_episodes.py与case_outputs.py；保留s02a/s02b并行与s03层级三问。

具体做法：
- 每个局部尝试都有唯一id、角色/对象、目的效果、核心区间、前后状态、局部结果和证据。
- 一次清障若由“抓取→移动→释放”串行完成，应是一个完整实现内部的多个操作；不把这些片段当作可相互替代的R。
- R表示足以实现所声明局部效果的一种完整做法。多个来源示范可以支持同一个R；不同方法由模型解释差异及效果对齐。
- 重试保留为不同尝试。同视频的两次靠近不因同名被合并。
- 未观察动作不得变成observed；显式政策允许的rule_only仍无观察证据、结果未知、不进入成功样本计数。
- 预期C_post与实际观测结果分开，模型置信度不当作成功率。

验收：
- [ ] “先失败后成功”测试中两次尝试和局部结果都能保留。
- [ ] “整体失败但局部抓取成功”不会把抓取改为失败。
- [ ] 串行实现片段不能冒充两个可替代实现。
- [ ] 同步前观察分支不因后续意图改判而被覆盖。
- [ ] 已有SVG/HTML与七字段输出仍可生成。

具体做法：

- 上下文证据只在声明的时间范围、对象和样本引用内使用，不能借其他技能的成功给本技能作证。

验收：

- [ ] 四种结果均可入池；未执行没有机会/原因证据时保持待定，不计执行失败。
- [ ] 缺少媒体、遮挡或证据冲突有明确未决项；不伪造反例。

### US-004：分开成功任务主图与完整条件对照，并完善条件/R归纳（P1）

作为使用者，我希望学习成功做法，同时利用失败尝试查明限制条件。

- video2op/semantic_aggregation.py的s10/s11/s12输入、输出、来源覆盖校验与export。

具体做法：
- 保存完整source_instances与source_paths，不修改原始结果。
- 模型为每个实例给出主去向：成功流程、仅条件对照、未执行、未决或任务范围外，并附理由。主去向守恒检查替代“全部必须进入主图”。
- s12成功主图只纳入获目标证据支持的成功流程；失败/未知不伪装成成功实现。整体失败视频中的局部成功仍可支持局部技能。
- 删除失败尝试后，新的跨越连接标记为基于来源路径的投影/候选，并保留被略过片段，不能冒充原视频里直接观察到的边。
- 简化成功流程由Qwen提出，保留被省略步骤、依据和依赖校验；不按固定模板自动删步骤。
- s10输出前置/约束/后置条件的提升、保留、否定、待定决策，记录支持、反例、可比范围及缺口。
- 保留现有必要性反例规则：条件F而成功可反驳必要性；失败本身不证明原因；未执行不是失败。
- 无对照时允许技能级C_pre/C_const为空。后置效果的语义对齐不与“必要前提成立”混用同一证明标准。
- s11输出语义约束、完成/过程/实现适用性评价及各层时序，控制器/检测器保持unbound。
- s12按目的、对象角色和效果归并功能。同动作异目的不合并；Push/Pull/GraspMove只有获得效果与条件对齐证据时才成为同技能的不同R。
- 若多段来源属于一个完整实现，先建立该实现的完整来源子图与关系，再导出；不靠随意的边并集生成新做法。

验收：
- [ ] 所有来源实例都有明确去向，没有静默遗漏。
- [ ] 失败尝试不在成功主图中，但能在条件证据中完整检索。
- [ ] 未知流程不会作为已确认成功示范。
- [ ] 不能把连续片段直接当作替代R；R保留完整实现证据和局部适用条件。
- [ ] 技能共同条件不由各R条件取并集填充。
- [ ] 新组合只标候选，不能以主图走到END判定任务成功。

### US-005：补时序与rewrite校验，保持来源事实不被重排覆盖（P0）

作为使用者，我希望错误引用、反向时序和无依据的肯定结论在落盘前被拒绝。

拟改：
- video2op/case_graph.py的validate。
- video2op/semantic_aggregation.py的validate_graph/_require_policy_shape。
- 复用已有状态/对象对齐接口，不新增宿主的语义判断器。

具体做法：
- observed_order检查证据与关系两端技能的归属，以及是否与原子动作时间/操作层先后矛盾；使用实际引用区间，不用整个长技能的粗包络粗暴否定合法交叠。
- observed_overlap需有时间重叠支持；“可并行候选”不能写成已观察并行。
- maintain_until与precedence分别处理，不把持续约束当成前置环。
- rewrite必须检查授权；无论是否rewrite，端点/来源、guard、guard_truth、status及对象范围通用检查都执行。
- 默认只允许声明范围内的sequence→branch重述，任意反向/换端点须拒绝。新增政策边无来源时明标candidate，不借其他边引用充数。
- 同视频重复出现不能合并。跨视频同类节点合并若与状态上下文或来源次序冲突，要求模型拆分/声明冲突；显式政策与证据不可同时满足时停止，不通过放宽校验凑图。
- 判断“前一步效果支持后一步前提”的语义仍由Qwen提出证据映射，宿主检查引用、对象一致、时间、来源和真值。不能用字符串相等代替蕴含判断。

验收：
- [ ] 前次复现的单视频反向时序被拒绝。
- [ ] 带rewrite的反向边、缺guard、guard_truth伪写T、status写observed都被拒绝。
- [ ] allow_precedence_rewrite=false时显式rewrite不能通过。
- [ ] 合法观察交叠、内部并行、maintain_until及重复尝试不被错误拒绝。
- [ ] 规则补充不被统计为独立视频观察或局部成功。

### US-006：纠正门控数据与现有展示的关联，不改图形形式（P1）

作为使用者，我希望门控检查正确的条件，清障之后使用新状态重新检查抓取可行性。

拟改：
- 优先在G_semantic中明确guard_id/guarded_skill/condition_refs/check_context及gate_outcome；最终字段名随契约定稿。
- video2op/semantic_skill_render.py、case_graph.py仅修改语义数据到既有门控/详情组件的映射。
- 不更换flow_layout.py、cross_video_render.layout的布局算法，不重新设计SVG/HTML。

具体做法：
- “本次执行抓取前要检查的条件”与“已提升的技能普遍必要条件”分开。C_pre为空不等于不需要检查，也不应为画门控而制造通用条件。
- 正向守卫保持一致，例如“抓取条件满足”；T/F是边的选择值，U是当前证据未知，三者不混用。
- 初次靠近后检查抓取条件：T进入抓取，F走现有上方清障支路；清障后再次靠近，再用更新后的状态检查。
- 第一门控关联抓取条件，而非因F支路排在前面就关联清障技能。
- 未知条件保持未知；候选分支不代表已证明可自动选择。
- 继续不在结束节点前添加门控，结果评价留在E和任务结果中。
- 按现有卡片/详情承载完整R、条件与来源。修正“只取第一个来源片段”的数据选择，完整来源留在现有展开详情中，不新增一种图形形式。

验收：
- [ ] 第一门控详情指向抓取条件。
- [ ] 清障→再次靠近→重新检查→抓取的条件语义可追溯，检查使用清障后的状态引用。
- [ ] C_pre为空时仍能显示有依据的候选检查，而不伪造条件提升。
- [ ] T/F/U和候选状态显示一致，无末端门控。
- [ ] 浏览器检查现有节点点击、悬停、七元组与展开详情；样式、布局策略和交互方式保持现状。
